---
title: Troubleshooting webhooks
description: Diagnose missing deliveries, invalid signatures, retries, and disabled endpoints
---

Start by listing the endpoint:

```sh
curl "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/" \
  -u "$PROJECT_ID:$PROJECT_SECRET"
```

## No requests arrive

Check the endpoint record first:

- `enabled` must be `true` and `status` must be `active`.
- `eventTypes` must include `message.received`.
- The endpoint record's string `schemaVersion` must be `raw-inbound.v1` for
  Standard Webhooks delivery. It is distinct from the delivered raw envelope's
  numeric `schemaVersion: 1`.
- The event must belong to the same project as the registration.

Then check the destination:

- Use the final public `https://` URL. Spectrum does not follow redirects.
- Confirm every DNS answer is public. Private, loopback, link-local,
  carrier-grade NAT, unique-local IPv6, and cloud-metadata ranges are blocked.
- Confirm the TLS certificate is valid for the registered hostname.
- If your firewall has an allowlist, include every address returned by
  `GET /projects/{projectId}/webhooks/egress-ips`.

A trailing-slash redirect is still a redirect. Register the URL that handles
the `POST` directly.

## Signature verification fails

The most common cause is body mutation. Verify the exact request bytes before
JSON parsing, decompression, whitespace normalization, or character conversion.

Also confirm that:

- you are using `standardSigningSecret`, including its `whsec_` prefix;
- the signed values come from `webhook-id` and `webhook-timestamp`;
- the HMAC output and header digest are Base64, not hexadecimal;
- your parser checks every space-delimited `v1,...` value during rotation; and
- the server clock is synchronized and inside your timestamp tolerance.

The legacy `signingSecret` works only with `X-Spectrum-Signature` and its
different `v0:` construction. Do not mix the two secret/header formats.

See [Verifying signatures](/webhooks/verifying-signatures) for a complete
implementation.

## The same event arrives more than once

At-least-once delivery permits duplicates. A handler can finish its work while
Spectrum loses the response or reaches its timeout, causing another attempt.

Use `webhook-id` as a unique idempotency key and acknowledge immediately after
durably enqueueing the event. Do not wait for slow downstream APIs before
returning `2xx`.

## Spectrum keeps retrying

Check the responses and errors recorded by your endpoint. Spectrum retries
`404`, `408`, `429`, `5xx`, network errors, DNS failures, and timeouts. It
honors valid `Retry-After` values within the four-day retry budget.

- Return `2xx` only after accepting responsibility for the event.
- Return `429` with `Retry-After` for intentional backpressure.
- Return `503` for a temporary outage.
- Return most other `4xx` responses for permanent request errors.
- Return `410` only to disable the endpoint.

## The endpoint is disabled

The endpoint record explains why:

| `disabledReason` | Cause |
| --- | --- |
| `manual` | Someone sent `{ "enabled": false }`. |
| `receiver_gone` | The endpoint returned `410 Gone`. |
| `delivery_failures` | Retryable failures continued for four days. |

Correct the endpoint, then re-enable it:

```sh
curl -X PATCH \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "enabled": true }'
```

Re-enabling resumes future delivery and any retries that are still pending in
the ordered endpoint lane. Spectrum does not currently expose terminal delivery
history or manual replay. Reconcile terminal failures from your own source of
truth after the endpoint is healthy.

## Rotation breaks some instances

During the overlap, `webhook-signature` contains signatures for both secrets.
Each instance only needs to match one. Make sure the verifier iterates over the
whole header rather than reading only its first token.

If old instances fail after `previousValidUntil`, the rollout did not finish
inside the overlap window. Deploy the new secret everywhere, then request
another rotation with a longer overlap if needed.
