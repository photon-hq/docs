---
title: Managing webhooks
description: Create endpoints, configure subscriptions, rotate secrets, and manage failures
---

Webhook management uses project Basic authentication:

```sh
-u "$PROJECT_ID:$PROJECT_SECRET"
```

One project can register multiple endpoints. Each endpoint has an independent
URL, secret, subscription set, retry lane, and enabled state.

## Create an endpoint

```sh
curl -X POST "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "webhookUrl": "https://example.com/spectrum",
    "schemaVersion": "raw-inbound.v1",
    "eventTypes": ["message.received"],
    "failureNotificationEmail": "webhooks@example.com"
  }'
```

`schemaVersion` pins the payload contract for the endpoint. It defaults to
`raw-inbound.v1`, which preserves the original provider request and uses
Standard Webhooks signatures. Choose `normalized-events.v1` only when you need
the original normalized Spectrum event shape.

This management field is a string endpoint schema ID. It is distinct from the
numeric `schemaVersion: 1` inside a delivered raw event, which identifies only
the revision of that envelope. Do not send the numeric value to this API or
compare the two fields.

The create response is the only time both `signingSecret` and
`standardSigningSecret` are returned. Store both before discarding the response.
For a `normalized-events.v1` endpoint, use `signingSecret` for current
deliveries and retain the complete `whsec_` `standardSigningSecret` for a future
upgrade to `raw-inbound.v1`.

Register the endpoint's final public HTTPS URL. A project cannot have two
active registrations for the same URL.

## List endpoints

```sh
curl "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/" \
  -u "$PROJECT_ID:$PROJECT_SECRET"
```

List responses do not contain signing secrets. They include:

| Field | Meaning |
| --- | --- |
| `eventTypes` | Events routed to this endpoint. |
| `enabled` / `status` | Whether delivery is active. |
| `disabledAt` | When Spectrum or an operator disabled it. |
| `disabledReason` | `manual`, `receiver_gone`, or `delivery_failures`. |
| `failureNotificationEmail` | Address notified after prolonged delivery failure. |
| `schemaVersion` | Pinned payload contract: `raw-inbound.v1` or `normalized-events.v1`. |

## Upgrade the payload schema

An endpoint using `normalized-events.v1` can upgrade once to
`raw-inbound.v1`:

Before upgrading, deploy the `standardSigningSecret` returned when the endpoint
was created. The PATCH response does not reveal it again, and raw inbound
delivery can begin as soon as the handoff completes.

```sh
curl -X PATCH \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "schemaVersion": "raw-inbound.v1" }'
```

The handoff makes the raw inbound destination visible before retiring the
normalized source. A delivery already in flight can still complete with the
previous schema. Schema downgrades are not supported.

## Configure subscriptions and alerts

`message.received` is the currently supported event type. New endpoints
subscribe to it by default. Set subscriptions explicitly so additional event
types can be introduced without changing where they are routed.

```sh
curl -X PATCH \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "eventTypes": ["message.received"],
    "failureNotificationEmail": "on-call@example.com"
  }'
```

Set `failureNotificationEmail` to `null` to remove the notification address.

## Disable or re-enable an endpoint

Disable delivery without deleting the registration:

```sh
curl -X PATCH \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "enabled": false }'
```

Manual disablement records reason `manual`. A receiver response of `410 Gone`
records `receiver_gone`; exhausting the four-day retry budget records
`delivery_failures`.

After correcting the endpoint, re-enable it:

```sh
curl -X PATCH \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "enabled": true }'
```

Re-enabling clears the disable reason. Future events and any retries still
pending resume in endpoint order. Spectrum does not currently expose terminal
delivery history or manual replay; reconcile terminal failures from your own
source of truth.

## Rotate the Standard secret

Rotation replaces only the Standard Webhooks secret. The legacy
`X-Spectrum-Signature` secret stays unchanged.

```sh
curl -X POST \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID/secret/rotate" \
  -u "$PROJECT_ID:$PROJECT_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "overlapSeconds": 86400 }'
```

The response returns the new `standardSigningSecret` once and a
`previousValidUntil` timestamp. During the overlap, every
`webhook-signature` header contains one signature for the new secret and one
for the previous secret.

A safe rotation sequence is:

1. request a rotation with enough overlap for your deployment;
2. store and deploy the new `whsec_` secret;
3. confirm the new secret verifies production deliveries; and
4. remove the old secret after `previousValidUntil`.

`overlapSeconds` defaults to one day, can be zero for immediate revocation, and
cannot exceed seven days.

## Retrieve egress addresses

```sh
curl "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/egress-ips" \
  -u "$PROJECT_ID:$PROJECT_SECRET"
```

Allowlist every returned IPv4 address. Query this endpoint when updating your
firewall instead of relying permanently on a copied list.

## Delete an endpoint

```sh
curl -X DELETE \
  "https://spectrum.photon.codes/projects/$PROJECT_ID/webhooks/$WEBHOOK_ID" \
  -u "$PROJECT_ID:$PROJECT_SECRET"
```

Deletion invalidates the registration and its secrets. A request already in
flight can still finish. Registering the URL again creates a new endpoint id
and new secrets.
